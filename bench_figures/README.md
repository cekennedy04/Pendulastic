# Bench analysis: phone IMU vs 1 kHz encoder — step by step

This folder reproduces every encoder-vs-phone number and figure in the September decks
(`September_Pendulastic_Progress_NEW_SLIDES.pptx`, `Pendulastic_Characterization_and_Cohorts_SLIDES_v3.pptx`)
and the publication set in `figures/publication_2026-09/`.

```
bench_figures/
  make_ssr_tables.py   step 1 — tracker workbook  ->  ssr_steps.csv, ssr_qa_joined.csv
  bench_figs.py        steps 2–6 — all analysis + figures (static, dynamic, PID, cohort, markerless)
  deck_figs.py         the three September-deck figures (fig_ssr, fig_physics, fig_anglefix)
  static_extra.py      extra static evidence: residual structure, whole-waveform RMSE, inside-a-hold zoom
  dynamic_extra.py     extra dynamic evidence: transient Bland-Altman, angular velocity, frequency response, ring after every step
  pubstyle.py          shared palette / fonts; PUB=1 switches to publication output
  inputs/ssr_encoder_qa.csv   overshoot / ring per encoder trial (from the PID sweep)
  *.csv                derived tables the figures read (regenerated by the steps below)
```

Run everything from the repo root with the project venv:


## 0. What the data is, and where it lives

| Signal | Location | Format |
|---|---|---|
| **Encoder (truth)** | `Pendulastic_Mobile_App_Trial/ck_9_14_pt/*.bin` | LabVIEW binary, 1 kHz, 7 interleaved float64 channels: `time, position (deg), velocity (deg/s), position_setpoint, torque, emg_fds, emg_edc` |
| **Phone (under test)** | `Pendulastic_Mobile_App_Trial/*.jsonl` (SSR session, "QUICK-TEST") and `Session_3/`, `Session_4/` | one JSON per sample: `{"t":…, "sensor":"gyro"|"accel"|"mag", "v":[x,y,z]}`; `v[1]` = gyro about the swing axis (rad/s) |
| **Session manifest** | `*-manifest.json` next to the JSONLs | lists trials with `file` + `timestamp` — **sort by timestamp to get true capture order; the phone's trial numbers are scrambled** |
| **Tracker** | `Downloads/Bench_SSR_Static_FILLED_DYNAMIC.xlsx` (or the CK Final tracker — same tab) | sheet `SSR Step-Response`: one row per settled step with encoder Δ, IMU Δ, drift, PID config |

Two encoder families in `ck_9_14_pt/`:
- `ck_ssr_pt_testStretchTrialNNFast.bin` (trials 21–115) — the **SSR staircase** `0 → +37.5 → −37.5 → +37.5 → 0`, 3 s holds. Static + step-dynamics data.
- `ck_9_14_ptStretchTrialNNSlow.bin` (01–20) — **lift at 100 °/s, loop rings on the raised arm, slow return**. Dynamic waveform data.

**The phone angle everywhere is the raw-gyro integral about the swing axis** (`phone_angle()` in `bench_figs.py`):
trapezoid-integrate `v[1]` in deg/s, zero on the first 40 samples. It is *not* the app's fused angle — on the
horizontal rig the swing rotates about gravity, so the accelerometer has no in-plane reference and the fused
angle is unassessable there (see the limitation slides).

Decoding an encoder file is one call:

```python
from labview_bin_reader import read_labview_bin
e = read_labview_bin("Pendulastic_Mobile_App_Trial/ck_9_14_pt/ck_ssr_pt_testStretchTrial72Fast.bin")
e["time"], e["position"], e["velocity"], e["position_setpoint"]
```

## 1. Tracker → per-step table (`make_ssr_tables.py`)

1. Open the tracker's `SSR Step-Response` sheet with `openpyxl` (`data_only=True`); row 4 is the header.
2. Keep rows with a numeric `Encoder Δ`; coerce the numeric columns.
3. Derive `Δ error = IMU Δ − Encoder Δ` and `|Δ err|` yourself (the sheet holds them as formulas that may not be cached).
4. Write `ssr_steps.csv`. Expect **180 rows, 176 with both deltas, 44 recordings** (the 4 NaN rows are trial 115).
5. Join `inputs/ssr_encoder_qa.csv` (overshoot %, ring °, settle s per encoder trial) to each recording's `P, I, D, Step speed` → `ssr_qa_joined.csv` (45 matched recordings). Only the PID figures need this.

---

## 2. Static accuracy (`st_scatter`, `st_bland`, `st_err_drift`)

All three read `ssr_steps.csv` after `dropna` on the two deltas.

- **Scatter** — IMU Δ vs encoder Δ, coloured by step speed; `np.polyfit` for gain, `corrcoef²` for R²; the note box prints n / gain / R² / mean |err| / max.
- **Bland–Altman** — `d = IMU − encoder`, bias = `d.mean()`, limits = `bias ± 1.96·d.std(ddof=1)`, plotted against |step magnitude|.
- **Error + drift histograms** — `|Δ err|` and `|Drift °/s|` columns.

`static_extra.py` adds three more: **st_structure** (error by step type / capture order / vs in-hold drift — medians within 0.3° of zero, session trend +0.04°, r vs drift −0.03), **st_wave_rmse** (whole-recording RMSE on every aligned 10 ms sample: median 0.58° at 200 °/s, 1.43° at 250 °/s; 95 % of 25,334 samples within ±3.3°), **st_hold** (three holds zoomed: 0.04° SD noise once settled — the error is a constant offset from the step transient).

Headline numbers you should reproduce: **mean |err| 0.58°, max 3.7°, gain 0.997, R² 0.9998, bias −0.03° ± 1.71°, 84 % of steps < 1°**; 200 °/s steps 0.40°, 250 °/s steps 0.77°.

## 3. Pairing a phone recording with its encoder file

This is the step that goes wrong most easily. Two rules, one per session type:

**SSR session (QUICK-TEST, 46 phone files ↔ Fast bins 21–115).** Sort the manifest by `timestamp`; phone capture-rank
*k* ↔ encoder trial ***k + 68*** (rank 2 → trial 70, …, rank 46 → 114). `ssr_pairs()` in `bench_figs.py` does this.
Index-window matching (what `bench_dynamics.py` does by default) mismatches most of them — the phone export order
is unrelated to the encoder numbering.

**Motor_9_14 session (Session_3, 15 phone files ↔ Slow bins).** No fixed offset; `motor_pairs()` cross-correlates
each phone angle against the Slow files within ±4 of its rank and keeps the best Pearson r. Ranks 1–8 pair at
r = 1.000 (repeatability repeats of one setting, so several map to the same encoder file — that is fine for
waveforms). Ranks 9–15 are release ring-downs whose encoder logs (`ck_9_14_pt_z…`) are **not on disk**; they have
no truth and are excluded.

**Time alignment** (`align()`): resample both to 10 ms, mean-remove, `np.correlate(encoder, phone, "full")`;
the lag at the peak gives `phone_time + lag = encoder_time`, its sign gives the mounting orientation, and the
Pearson r on the overlap is the pairing quality (keep ≥ 0.99 for figures).

---

## 4. Static waveforms (`st_wave`)

For each step speed pick the two best-aligned recordings (highest r), overlay encoder (black) and phone (teal)
on the encoder time base, and print mean / max |phone − encoder| over the overlap in the panel title.
Expect r ≥ 0.9997 and mean errors of 0.2–1.1°.

## 5. Dynamic analysis

### 5a. Step transients (`dy_step`) — SSR session, same estimator both sides
1. Pair by the *k + 68* rule; keep r > 0.98.
2. Find step starts from the **encoder setpoint**: `|d setpoint/dt| > 1 °/s`, then keep one start per step with a 1 s refractory (the setpoint is a ramp, so it "starts" on every sample otherwise).
3. For each step, on both traces: `frm` = median over 0.3 s before `t0`; `to` = median over the last 1 s before the next step; normalise `x = (θ − frm)/(to − frm)`; **rise** = t(0.9) − t(0.1); **overshoot** = (max x − 1)·100; **settle** = last time |x − 1| > 0.02, minus `t0`. Steps under 5° are skipped.
4. Scatter phone vs encoder per metric; note box gives median |Δ|.

Expect 172 steps / 43 recordings; median |Δ| **rise 0.006 s, overshoot 1.1 %, settle 0.016 s**.

`dynamic_extra.py` adds four more on the same pairs (r > 0.98, 168 steps): **dy_bland** (Bland–Altman per metric: rise −4 ± 14 ms, overshoot +1.1 ± 2.0 %, settle −0.11 ± 0.94 s), **dy_velocity** (peak angular velocity phone-rate vs encoder-derivative: gain 1.011, R² 0.9998, bias +4.5 °/s; sample residual flat vs speed), **dy_bode** (pooled Welch cross-spectrum H = Pxy/Pxx over 49 recordings at 100 Hz, nperseg 512: gain 1.003 ± 0.004 in 0.5–1.5 Hz, coherence > 0.9 to 4.9 Hz, +2.5 ms residual delay), **dy_ring_steps** (ring after every step, 0.2–1.3 s window, extrema ≥ 4: 94 rings at 4.3–6.1 Hz, median |Δf| 3.2 % — quantised by the phone's ~59 Hz sample rate).

### 5b. Dynamic waveforms vs encoder (`dy_wave`) — Motor_9_14 lift-and-ring trials
1. `motor_pairs()`; keep r ≥ 0.999.
2. Lift time = first encoder |velocity| > 40 °/s in the overlap; zero **each trace at its own pre-lift rest** (median 0.8–0.1 s before the lift) — do not zero on the tail, the slow return moves it.
3. Ring frequency: window 0.35–3.0 s after the lift, remove a linear trend, count zero-crossings → f = (crossings − 1) / (2·span). Identical code on both traces.
4. Mean |phone − encoder| over lift − 0.5 s → lift + 4 s.
5. Figure: full overlay of one swing, two ring zooms, phone-vs-encoder f scatter.

Expect 7 swings, **median |Δf| 0.4 %, mean |err| 0.72° (median swing), rings 1.9–3.3 Hz**.

### 5c. Hand-pulled swings, f ∝ √P (`dy_physics`, `dy_amplitude`) — Session_4, phone only
1. Sort the Manual_9_14 manifest by timestamp → run order 1–18. Run order → P and pull angle from the tracker's Trials sheet: runs 1–3 and 16–18 P = 1, runs 4–15 P = 0.1; pull 30° except runs 10–12 (40°) and 13–15 (50°).
2. These recordings **start with the arm already held at the pull**, so: release = first |rate| > 40 °/s; rest = median of the last 1 s (that is the motor's zero); pull = |θ(release) − rest|.
3. f from the alternating extrema of θ − rest with threshold max(5 % of first peak, 0.5°): f = (n_extrema − 1) / (2·(t_last − t_first)). (An FFT on a 4 s Hann window under-reads fast-decaying rings — that is why the earlier 0.95 / 2.97 Hz numbers differ.)

Expect **P 0.1 → 1.09 Hz (SD 0.005), P 1 → 2.87 Hz, ratio 2.64× vs √10 = 3.16**; pull 30/40/50° → 30/40/52°.

## 6. PID figures (`pid_speed`, `pid_explainer`)

`pid_speed` reads `ssr_qa_joined.csv`: overshoot vs commanded step speed (200 vs 250 °/s), and overshoot vs P
with I and D swept — flat. `pid_explainer` is a labelled simulation of a damped oscillator (P = spring, D = brake)
plus two real encoder steps (200 vs 250 °/s) decoded from trials of each speed. Expect medians **4.4 % vs 19.2 %**.

---

## 7. Adding new bench recordings

1. Export the phone JSONLs + manifest into a new `Session_N/`; put the encoder `.bin`s in one folder.
2. Add the rows to the tracker's `SSR Step-Response` tab (static) or note the capture order (dynamic).
3. Re-run step 1, then `ONLY=st_ bench_figs.py` (static) or add a `*_pairs()` function using `align()` for the new session and reuse `dy_wave()`.
4. Record a **sync tap** at the start of each new recording — the current alignment is cross-correlation only, so it gives shape agreement, not absolute latency.
