Grounding Context

Codebase context. pendulastic_app.py (~3,900 lines) is the sole clinician-facing entry point (a standalone duplicate Workbench entry point was removed earlier this session, after it was found to have silently drifted — WorkbenchView.reset_for_new_trial() went uncalled for an unknown period). src/pendulastic/ (~983 lines) is a real, maintained-looking package that none of the production files import from. The repo root carries 95+ stray training/eval log and zip files. An active nightly hygiene automation (run_nightly_hygiene.ps1, a Windows Scheduled Task) writes categorized cleanup manifests to docs/reports/ and never auto-applies. The 2026-08-13 report has open [Needs Review] and [Doc Drift Fix] items unresolved across multiple reports. IMPACT_MEASUREMENT_REPORT.md (2026-08-05) names concrete, still-outstanding follow-up work: RMSE-improvement quantification, drift-magnitude correlation.

Directly observed this session. Two independent test flakes were confirmed by hand: a Tcl/Tk resource-exhaustion TclError (tests/test_app.py::test_on_source_changed_does_not_crash) and a Windows heap-corruption crash 0xc0000374 (tests/test_app.py::test_on_back_to_mode_select_resets_state, in camera_utils.py's _read_loop/_on_camera_status) — both reproduce only under long batch test runs and pass clean in isolation.

External context (web research, value: high). No modern markerless-video pendulum-test study specific to Multiple Sclerosis was found — a real positioning gap. OpenCap and Pose2Sim are open-source packaging/delivery precedents; Kinovea is the closest UX analog (lightweight desktop tool, no IT overhead, large PT/sports-medicine adoption). DARI Motion holds an FDA 510(k) clearance for markerless CV-only motion analysis — a real regulatory precedent for this device category. A 2025 Parkinson's shoulder-girdle rigidity study fuses model-driven and data-driven features on a structurally similar passive-oscillation task, correlating r=0.78 with UPDRS.

1

Give hardware-touching tests their own process — stop finding crashes by accident

Axis: Test/CI reliability Confidence: 85% Complexity: Medium
Description
Add @pytest.mark.gui/@pytest.mark.hardware markers separating Tk- and camera-touching tests from pure-logic tests; run the marked tier in process isolation with real teardown between tests instead of accumulating state across a single long-lived interpreter; add a nightly soak job (riding the same unattended-runner pattern as the existing hygiene automation) that runs the marked tier repeatedly and keeps a flake-frequency ledger. As a further-out stretch: treat live camera capture the same way production audio workstations treat native plugin hosts — run it in a separate process so a driver-level crash kills a restartable child, not a live recording session.
Basis
direct: both flakes were independently confirmed and reproduced this session — a Tcl/Tk TclError in tests/test_app.py::test_on_source_changed_does_not_crash and a Windows heap-corruption crash 0xc0000374 in tests/test_app.py::test_on_back_to_mode_select_resets_state (camera_utils.py's _read_loop/_on_camera_status), both passing clean in isolation and failing only under a long batch run. A verifier independently confirmed no .github/workflows/ or pytest marker config exists in the repo. reasoned: a Windows heap corruption in a camera read loop is not a test artifact — it's the exact code path that runs during a real acquisition, so this is a patient-facing reliability risk wearing a "flaky test" costume.
Rationale
Both known flakes were found by accident, mid-session, doing unrelated work — without any isolation or soak mechanism, that's the only way this class of failure surfaces, which means more are plausibly hiding the same way. Fixing the isolation boundary once removes an entire category of future flakes instead of chasing each one as a one-off.
Downsides

Process-isolated test execution is slower to iterate on locally and adds real infrastructure work. Out-of-process camera capture is a materially bigger architecture change and should be scoped as a separate follow-on, not bundled into the first pass — the marker + isolation + soak-ledger piece is the actionable near-term slice.

2

Replace scattered silent failures with one clinician-visible integrity channel

Axis: Clinician-facing product features Confidence: 80% Complexity: Low–Medium
Description
At least three independent sites in the clinician-facing app silently swallow failures with no signal to the user. Rather than patching each site with its own message box, introduce one shared mechanism: a per-trial integrity record that every degraded path appends to (a dropped sample, a failed render, a coerced value), surfaced as a small non-blocking status indicator on the trial and serialized into whatever export the session produces. A natural extension once this exists: stamp the code version and input hashes into the same record, giving every exported result a lightweight provenance trail.
Basis
direct: verified by the basis-verification pass — pendulastic_app.py:2333-2337 and :2605-2609 both wrap matplotlib figure cleanup in except Exception: pass; workbench_engine.py:367-370 silently drops malformed IMU sample lines via except ValueError: continue. All three citations were independently re-verified and confirmed exact.
Rationale
This is a clinical measurement tool — a clinician who reviews a trial with 140 silently dropped samples currently sees the same thing as one with zero dropped samples. That's a data-validity defect wearing a UI-polish costume, and it silently affects the very ICC/Bland-Altman numbers the project's own validation work depends on.
Downsides

Requires touching several call sites across two files and agreeing on one shared shape for "degradation event" before any of them can use it — the design decision (what counts as reportable, how loud the indicator is) takes more thought than the mechanical wiring.

3

Resolve src/pendulastic's limbo — then add a tripwire for the next silent drift

Axis: Repo hygiene & structure Confidence: 75% Complexity: Medium
Description
src/pendulastic/ is ~983 lines of real, apparently-maintained code that none of the three production entry points import. Decide its fate on purpose instead of by accident: either consolidate genuinely duplicated logic into it (a confirmed concrete target — two near-identical _show_figure methods in pendulastic_app.py share the exact same silent-exception pattern) so it becomes the project's real, Tk-free, independently-testable scoring core, or delete it. Either way, add a small comparator/lifecycle-hook test for the remaining near-duplicate pairs in the codebase (e.g. imu_calibration_tuner.py vs pendulastic_imu_server.py) so a future silent divergence fails a test instead of surfacing months later.
Basis
direct: confirmed via the verification pass — two near-identical _show_figure methods exist at pendulastic_app.py:2327 and :2598, sharing duplicated try/except-close/pack logic. direct: this exact failure class already bit the project once this session — WorkbenchView.reset_for_new_trial() was silently uncalled in the surviving App after a duplicate entry point was removed, undetected until this session, with no test catching it.
Rationale
An unused parallel package sitting next to the code it seems to duplicate is the same risk that just cost real debugging time, in slow motion — someone edits one copy thinking it's live, or copies logic between them and creates a second source of truth nobody notices drift apart. A comparator test converts an unenforceable convention into a mechanical check.
Downsides

The "promote to real library" direction is the more ambitious of the two resolutions and carries real refactor risk if pursued fully — it's worth scoping as its own bounded piece of work rather than deciding it in the same pass as writing the comparator tests, which are cheap and low-risk regardless of which resolution wins.

4

One-off empirical RMSE comparison — automate later only if it earns it

Axis: Validation & regulatory positioning Confidence: 65% Complexity: Medium
Description
Revised after a second independent review (Codex) pushed back on the original framing of this idea, which proposed a nightly automated "golden-trial" job. That review is right: workbench_engine.py's _read_jsonl_samples/_replay_samples are only replay primitives — they don't constitute a validation pipeline on their own. Missing: a versioned golden cohort with matched OptiTrack reference, a defined pre-change baseline, alignment + RMSE computation, and acceptance/failure criteria. Build that manual (or CI-on-change) comparison first: a locked trial manifest, old-vs-new configuration, paired per-trial RMSE, an aggregate effect with uncertainty, and explicit failure criteria. Only promote it to a scheduled job later if it proves useful and stable on its own — and never couple it to an unattended, elevated-permission automation harness (see the dropped idea below).
Basis
direct: confirmed via verification — _read_jsonl_samples (workbench_engine.py:360) and _replay_samples (:374) exist and do deterministic offline replay, but are replay primitives only. direct: IMPACT_MEASUREMENT_REPORT.md (2026-08-05) marks "RMSE Improvement Expectation: VALIDATED" but that is a design-analysis validation only; its own Recommendations section still lists "Measure impact (first month): Quantify average RMSE improvement across the Pendulastic family" as forward-looking, unactioned work — still open as of 2026-08-16. reasoned: (Codex, verified against the repo before opining) replaying a fixed corpus nightly has near-zero value unless code/config actually changes — it is a regression test, not new clinical evidence, and cannot manufacture post-deployment evidence on its own if no new labeled trials arrive.
Rationale
The underlying gap is real and worth closing — the project's own report committed to an empirical measurement that's now 11+ days overdue. But the fix is building the actual comparison (which has genuine scientific value), not scheduling an automated job around primitives that don't yet add up to one. Two independent reviewers (a ce-pov second opinion and Codex, reading the code directly) converged on this same correction.
Downsides

Defining a real golden cohort, baseline, and acceptance criteria is genuine work, not a quick wire-up — this is more effort than the original "reuse existing replay code" framing implied, which is reflected in the lower confidence and higher complexity versus the original version of this idea.

5

Three cheap regulatory-readiness moves that get expensive after the first outside reviewer looks

Axis: Validation & regulatory positioning Confidence: 75% Complexity: Low (each) / Medium (as a bundle)
Description
Three distinct, individually cheap moves that share one underlying gap — this project will eventually face outside scrutiny (publication, a future clinician user, possibly a regulatory reviewer) and isn't yet ready for it in three specific, fixable ways. (a) Participant governance: stand up a minimal consent/enrollment schema and gate the validation pipeline on it, rather than a hardcoded, unjustified minimum-cohort constant pointed at an empty registry. (b) Intended-use framing: the app already emits a predicted clinical grade — decide the framing now (label it explicitly as a research estimate, always show the underlying continuous score) rather than let the current UI silently make that classification decision by default. (c) Reproducibility contract: define one command that regenerates a result from pinned inputs, since today nothing outside one Windows laptop can reproduce a single figure.
Basis
direct: confirmed via verification — participant_groups.json is literally {}; mas_validation.py:84 has _MIN_N_FOR_CONFIDENCE = 5 with no attached rationale. direct: pt_to_mas() (pendulastic_pt_score.py:231-234) is a pure threshold lookup with no uncertainty/disclaimer output — a repo-wide search for "research estimate," "not a diagnos*," "investigational" found zero matches. external: DARI Motion's existing FDA 510(k) for markerless CV-only motion analysis establishes this device category does get regulated. direct: no .github/workflows/ exists; the nightly automation is hardcoded to one machine and path; README.md says "citation forthcoming upon publication."
Rationale
Every one of these three is a free decision today and an expensive retrofit later. The window to add participant governance and reproducibility closes the moment the first real publication cohort is collected; the intended-use framing is being set right now, by default, through what the app happens to print on screen.
Downsides

None of these are hard engineering — the risk is treating them as one big bundled project instead of three independent, quickly-shippable decisions. Sequence them separately rather than waiting for a single "regulatory readiness" epic.

6

Fuse video and IMU into one estimator instead of picking a winner

Axis: Validation & regulatory positioning (touches clinician features) Confidence: 55% Complexity: High
Description
The app currently picks exactly one modality to score a trial from, via a fixed priority list — IMU and video are treated as competing sources where one wins, and the rest of the multi-modality apparatus exists purely to prove they agree. Explore a hybrid model-driven (damping ratio, decay rate) plus data-driven fusion that uses both as complementary features of one estimator, following published precedent on a structurally near-identical passive-oscillation measurement task.
Basis
direct: confirmed via verification — _PT_SOURCE_PRIORITY = ["imu", "rgb", "optitrack", "hpe_upload", "video_file", "upload_csv"] at pendulastic_app.py:1598, a genuine single-pick priority list, not a fusion. external: a 2025 Parkinson's shoulder-girdle rigidity study fuses model-driven damping/decay features with a data-driven model on a passive-oscillation task, correlating r=0.78 with UPDRS — the same underlying physics (damped oscillation quantifying involuntary muscle tone) and the same clinical-scale replacement goal.
Rationale
This is the boldest idea in the set, and it's the strongest candidate for actually owning the "markerless pendulum test in MS" positioning gap the web research surfaced — no modern study does this for MS specifically, and a genuinely fused measurement (not just a video-only or IMU-only one validated against the other) would be a real scientific contribution, not an engineering polish item.
Downsides

This is a research question, not a build task — there's real uncertainty about whether fusion actually outperforms the best single modality on this specific measurement, and answering that needs an actual experiment with the existing multi-modality dataset before any product commitment. Confidence is lower here than the other six ideas for exactly that reason.
